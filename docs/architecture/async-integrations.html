Асинхронные интеграции

1. Концепция взаимодействия​

Для обеспечения высокой отказоустойчивости и снижения связанности (decoupling) система использует событийно-ориентированную архитектуру (EDA).

Почему асинхронность?​

  • Гарантия доставки: Если сервис уведомлений или внешняя система деканата временно недоступны, сообщение сохранится в очереди брокера.
  • Производительность: Основной API не ждет завершения тяжелых процессов (например, рассылки 5000 push-уведомлений), а мгновенно возвращает ответ пользователю.
  • Масштабируемость: Мы можем увеличивать количество обработчиков (consumers) очереди при пиковых нагрузках.

2. Технологический стек интеграций​

  • Брокер сообщений: RabbitMQ.
  • Формат данных: JSON.
  • Протокол: AMQP 0-9-1.

4. Общая схема потоков (Data Flow)​

  1. Producer: Сервис ядра (Core Service) публикует событие в Exchange (например, schedule.events).
  2. Exchange: На основе ключа маршрутизации (Routing Key) распределяет сообщение по очередям.
  3. Consumer: Сервис-подписчик (например, Диспетчерская) забирает сообщение, обрабатывает его и отправляет подтверждение (ACK).

5. Обработка ошибок (Dead Letter Exchange)​

Если сообщение не может быть обработано после 3 попыток, оно автоматически перемещается в DLX (Dead Letter Exchange). Это позволяет инженерам вручную проанализировать проблемные данные, не блокируя работу основной очереди.
